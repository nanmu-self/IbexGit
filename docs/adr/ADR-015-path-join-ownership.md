# ADR-015：目标路径拼接的归属层（前端 joinPath vs 后端 Path::join）

- **状态**：提议（Proposed）
- **日期**：2026-10-06
- **相关**：ADR-009（tauri-specta 类型同步）、ADR-002（Svelte 5 Runes）
- **触发**：CloneDialog「目标位置」交互缺陷修复时暴露的架构问题

---

## 1. 背景

修复「克隆远程仓库」弹窗的目标位置交互时，发现前端存在两处各自实现的路径拼接逻辑，
且分属两个对话框：

| 位置 | 原实现 | 判据依据 |
|---|---|---|
| `NewRepoDialog.svelte` | 本地私有 `sep()` | `dir.includes("\\") \|\| navigator.userAgent.includes("Windows")` |
| `CloneDialog.svelte` | `dest` 单字段，选择器返回值原样透传 | 无判据（不拼接） |

问题有三层：

1. **同一份路径在两处可能拼出不同形态**（同一界面、同一意图、两种结果）。
2. **判据把代码绑死在 WebView 的 UA 默认值上** —— 外部依赖，退化时静默无感。
3. **DTO 契约层面没有"路径由谁拼"的约定** —— 这是本文要拍的核心问题。

本文只解决第 3 点。前两点已在同日修复（抽出 `src/lib/path.ts` 供两处共用），
属于本 ADR 的**前置动作**，不是结论本身。

## 2. 问题：拼路径这一层该归属哪一侧

「父目录 + 名称 → 最终路径」这个拼接，两侧都能做。

**方案 A：维持前端拼接（status quo）**
契约不动，后端按字面接收。

**方案 B：后端接 `(parent, name)`，用 `Path::join` 拼接**
改三个 DTO 契约，前端不再重复实现。

**方案 C：后端接 `(parent, name)`，自己写归一拼接（不用 `Path::join`）**
契约改动同 B，但输出形态由后端自己保证。

**方案 D：契约不动（维持 A），后端对收到的 `dest` 做纯校验**
见 §5—— 这是 ADR 初稿遗漏的中间档。

## 3. 关于 `Path::join` 的实测（**不构成否决理由**）

2026-10-06 本机（Windows）实测：

```
Path::new("C:/a").join("b")      = "C:/a\b"      ← 混斜杠
Path::new("/x/y").join("z")      = "/x/y\z"      ← 父目录正斜杠，输出反斜杠
Path::new("C:\\repos\\").join("p") = "C:\repos\p"  ← 尾斜杠被吸收
PathBuf::from("C:/repos/a/b").file_name() = Some("b")
```

`MAIN_SEPARATOR` 在 Windows 上是 `\`（`is_separator` 同时认 `\` 和 `/`），
`join` 只在 name 是绝对路径时丢弃 base，否则一律用 `MAIN_SEPARATOR` 追加，
**不对已有的正斜杠归一**。

**这为什么不是决定性证据：**

1. **混斜杠是展示问题，不是正确性问题**。混斜杠路径传给 git / Win32 API
   完全有效（`C:/a\b` 能正常创建与访问）。方案 B 下前端回显用 `path.ts`
   拼即可 —— **展示串 ≠ 传输串**，两者本就不必相同。
2. **分歧面比表格呈现的小得多**。前端判据是"路径自身形态"，
   `Path::join` 是"运行平台"，二者仅在 POSIX 风格路径上结论相反；但
   `/mnt/c/repos`、`/home/me/repos` 这类输入在 **Windows 侧不可达** ——
   文件夹选择器不返回 POSIX 路径，WSL 场景返回的是 `\\wsl$\...`（含反斜杠，
   两判据一致）。真正可达的分歧面只有 `C:/repos`（盘符+正斜杠），
   而该形态下两判据**结论相同**（都给 `\`）。

因此仅凭本节，"B + 前端自拼回显"是自洽的。这一节的作用是说明
**若将来采纳 B/C，输出形态需显式约定**，而非否决B。

## 4. 决策：方案 A（维持前端拼接）

### 4.1 首要理由：全库既有约定就是「前端构造完整路径、后端按字面接收」

这不是本 ADR 新立的规则，而是**已经在全库生效的事实**。
`bindings.ts` 中 `path: string` / `dest: string` 型命令参数共 **34 处**，
**无一处**使用 `(parent, name)` 结构：

| 命令 | 路径参数 | 形态 |
|---|---|---|
| `repo_init` | `path: string` | 前端拼好的完整路径 |
| `git_clone` | `dest: string` | 同上 |
| `repo_open` | `path: string` | 同上 |
| `workspace_touch_recent` | `path: string` | 同上 |
| `app_check_git_path` | `path: string` | 同上 |
| `git_file_content` / `blame` / … | `path: string` × 十余处 | 同上 |

> 计数口径：`grep -E "\b(path\|dest)\??: string"` 得 **45** 行匹配，其中
> **2 处不是命令参数**——第 486 行 `AppError::InvalidRepo { path }`（错误载荷
> 字段）与第 825 行 https 认证请求的 `path: string | null`（URL 路径，非文件
> 系统路径）。有效命令参数 = 45 − 2 = **33**；另`git_clone` 的 `dest` 写在
> 多行结构体里未被上述grep 计入，合计 **34 处**。改这个数字前先按此口径复核
> —— `grep -c` 数的是行数，直接当参数个数会多算。

单改 `clone` / `init` 两三个 DTO **统一不了约定**，只会造成“两类命令并存”：
34 处里改 2 处，其余 32 处照旧。之后**每个新带路径参数的命令都要重新
纠结一次**，且开发者无从判断该跟哪类看。

一致性论据，而非风险论据。

### 4.2 次要理由：UI 回显必须与提交值同源

方案 B 下，前端要显示最终路径给用户确认，**仍得自己拼一份**。于是
"两处拼接"的问题只是从"两个前端文件"变成"前端 + 后端"，原始问题
换个位置复活 —— 且这次跨了 FFI 边界，比现在更难排查。

方案 A 下回显串与提交串是**同一个值**（`joinPath` 的产物直接进
`net.clone({ dest })`），不存在分叉可能。

这是 B 最硬的否决点：**B 想消除的重复，在 A 下本来就不存在**；
B 引入的重复（展示 vs 传输）却是真实的。

### 4.3 附加理由

- `Path::join` 解决不了本次缺陷：根因是"选择器返回的目录被当成最终目录"
  —— **语义建模错误**，不是拼接方式错误。
- §3 已说明混斜杠不是正确性问题，不构成否决理由。

## 5. 方案 D：契约不动，后端对 `dest` 做纯校验

ADR 初稿把"拼接归属"与"校验归属"捆在一起，遗漏了这一档。实际上二者独立：

**B 宣称的收益"后端可在拼接前校验名称合法性"，不需要挪拼接就能拿到** ——
后端收到完整 `dest` 后拆分即可（§3 实测）：

```
PathBuf::from("C:/repos/a/b").file_name()   = Some("b")
PathBuf::from("C:/repos/..").file_name()     = None
PathBuf::from("C:/repos/CON").file_name()    = Some("CON")
```

注意 `a/b` 的 `file_name()` 是 `Some("b")` —— **单靠 `file_name()` 拦不住**
嵌套目录名，需比对形态（是否等于末段原始输入）或直接在完整串上判定。
这是方案 D 的实现要点，不是拦不住的否定理由。

**方案 D 的价值**：它把 §7 的重评路径变成**有梯度的**——
先 D（零契约成本），D 不够再升C / B；而不是像初稿那样从A 直接跳到全量契约改写。

**本次未实施 D**，作为 §7 触发条件 2 的第一响应。

## 6. 后果

### 6.1 正面

- `src/lib/path.ts` 是路径拼接与名称校验的唯一入口，纯函数、**已有断言覆盖**：
  `scripts/path.test.ts`（42 项，`node --experimental-strip-types` 直跑）。
  断言已入库（`.gitignore` 例外）并接入 CI 前端流水线（`pnpm test:unit`）。
- 两个对话框对同一份路径产出同一结果；名称规则同源。
- 尾斜杠归一消除「带不带尾斜杠 → 两种克隆落点」的分叉。
- `NewRepoDialog` 补上了名称校验（见 §6.3）。

### 6.2 代价（明确接受）

- **路径合法性校验只存在于前端**。`isSafeRepoName` 是 **UI 便利校验，
  不是安全边界**。后端目前不做名称校验 —— 若将来出现非 UI 调用方
  （CLI、脚本）直接调 `git_clone` / `repo_init`，需自行保证 `dest` 合法。
  → 记入技术债，触发条件见 §7。
- **两端各有一份"路径长什么样"的认知**：前端用于展示与拼装，后端用于 git 调用。
  靠本文约定 + 断言维持一致，无类型强制。

### 6.3 本次同时修掉的既有缺陷

`NewRepoDialog` 此前**只校验非空**，无任何名称规则。实测（Rust
`PathBuf` + 真实 `git init`）：手输 `a/b` 时 `create_dir_all` **静默创建
中间目录**，仓库落在 `a/b`，而 UI 回显的是 `base\a/b` —— **回显与落点
不一致**，恰是本 ADR 要消灭的那类"同一意图两种结果"。

已提为 `path.ts` 的 `isSafeRepoName`，两对话框共用（i18n key 亦提为共享的
`net.repoNameInvalid`）。

### 6.4 已知缺口

**前端规则未覆盖的形态**（当前无用户报障，仅记录）：

- **超长路径**：未做长度限制。Win32 有 `MAX_PATH`（260）限制，
  扩展长度前缀 `\\?\` 可绕过但 UI 未提示。
- **非 ASCII 名称**：未做长度按字节估算（部分 Win32 API 以字节为单位）。

**后端无对应校验**：`isSafeRepoName` 的规则**没有 Rust 侧对应实现**。
有意为之 —— 在 Rust 侧复刻一份规则意味着**第二份实现**，两份规则必然漂移。
§6.2 的未决项本身已提示校验应归位前端。若 §8 触发条件 2 发生，
方案 D 落地时 Rust 侧只做**最小必要校验**（拒绝 `..`、拒绝非单段名），
不复制完整保留名名单。

### 6.5 与决策无关的已知限制（原 §3 的 `to_string_lossy`，已移出计分）

`to_string_lossy` 对非 UTF-8 路径插入 `U+FFFD`。这**不是 A/B/C 的区分项**：
采用 A 时后端 `PathBuf::from(path)` 照样过 `to_string_lossy`（`repo_init`
里就有）；且非 UTF-8 早在 Tauri dialog 插件返回 JS 字符串那一步就已 lossy。
与拼接归属无关，仅记录。

## 7. 长期约定（本文的真正产出）

> **FFI 边界上，路径一律是完整、绝对、可直接回显的字符串。
> 构造在前端，存在性校验在后端，后端不做二次拼接。
> 后续新增带路径参数的命令沿用此约定。**

配套的校验归属：

| 关注点 | 归属 | 位置 |
|---|---|---|
| 拼接（分隔符、尾斜杠归一） | 前端 | `src/lib/path.ts::joinPath` |
| 名称合法性（UI 便利校验） | 前端 | `src/lib/path.ts::isSafeRepoName` |
| 存在性 / 非空（真实守门） | 后端 | `core/engine/cli.rs::clone_repo` 等 |

## 8. 重评触发条件（带梯度）

1. 出现第二个 `dest`/`path` 构造方（CLI、脚本、第三方调用）
   → 响应：**方案 D**（后端拆 `dest` 做纯校验）。
2. 需要在服务端区分"路径不合法"与"路径已存在"以给出不同错误
   → 响应：**方案 D**；D 不够时再评估 C / B。
3. 跨平台路径（非 UTF-8、UNC、超长路径）成为**已报问题**
   → 重新评估；注意 §6.5 说明其中非 UTF-8 部分与拼接归属无关。

## 9. 入库说明与既有 ADR 的记录缺口

`.gitignore` 以目录级规则忽略 `docs/` 与 `scripts/`。git 对被忽略的**目录**
不下沉，例外必须写成「`docs/*` + `!docs/adr/`」形态 —— 直接在 `docs/`
后加 `!docs/adr/` 永远不生效。已按此改写（`scripts/*` +
`!scripts/path.test.ts` 同理）：本 ADR 与 path.ts 断言无需 `git add -f`
即可入库；`docs/screenshots/` 下**新**文件仍被忽略，已跟踪文件不受影响。
